# Руководство по использованию METR на Git‑платформах

Этот документ описывает, как организовать работу с репозиторием METR на различных Git‑платформах, включая GitHub, GitLab, Bitbucket, Gitea/Forgejo и отечественные решения (например, GitFlic, self‑hosted GitLab CE, корпоративные инсталляции).

## 1. Цели и принципы

- **Нейтральность к платформе** — репозиторий не привязан к конкретному Git‑провайдеру.
- **Читаемость истории** — аккуратные коммиты, понятные ветки, минимизация «мусорных» merge.
- **Безопасность** — защита основных веток, обязательный code review.
- **Соответствие лицензии** — сохранение `LICENSE.txt` и `NOTICE.txt`, использование `LICENSE_METR.md`.

---

## 2. Структура репозитория (кратко)

Главные директории и файлы:

- `app/` — основной код клиента (React Native, TypeScript).
- `contracts/` — смарт‑контракты (Solidity).
- `docs/` — документация (включая этот файл и `METR_DOCUMENTATION_PORTAL.md`).
- `android/`, `ios/` — нативные проекты.
- `test/`, `detox/`, `scripts/` — тесты и утилиты.
- `README.md` — обзор METR и навигация по документации.
- `LICENSE.txt`, `NOTICE.txt`, `LICENSE_METR.md` — лицензирование и атрибуции.

Подробнее см. `docs/METR_DOCUMENTATION_PORTAL.md`.

---

## 3. Базовый Git‑workflow

Рекомендуемый рабочий процесс независим от платформы:

### 3.1 Ветки

- Основная ветка: `master` или `main` (в зависимости от конкретного зеркала/форка).
- Тематические ветки:
  - `feature/<кратко-описать-фичу>` — новые фичи.
  - `fix/<кратко-описать-фикс>` — исправления багов.
  - `docs/<кратко-описать-док>` — обновления документации.
  - `chore/<задача>` — инфраструктура, CI, утилиты.

Примеры:

```bash
# Создание ветки из основной
git checkout -b feature/ai-mood-ring

# Работа, коммиты и последующий push
git commit -am "feat(ai): add mood ring visualization"
git push origin feature/ai-mood-ring
```

### 3.2 Стиль коммитов (рекомендовано)

Используйте осмысленные сообщения, по возможности в стиле conventional commits:

- `feat(ui): add gesture navigation microinteractions`
- `fix(sync): handle offline edge cases`
- `docs: update METR documentation portal`

Это упрощает генерацию CHANGELOG и чтение истории.

### 3.3 Pull/Merge Requests

- Каждый PR должен сопровождаться описанием и ссылкой на задачу (если она есть).
- Используйте `PULL_REQUEST_TEMPLATE.md` как чек‑лист.
- Не объединяйте большие несвязанные изменения в один PR.

## 4. GitHub

### 4.1 Защита веток

Рекомендуемые настройки для основной ветки:

- Запрет прямых пушей (только через PR).
- Требование минимум одного review.
- Обязательный проход CI (если настроен).

### 4.2 Шаблоны задач и PR

В корне репозитория уже есть:

- `ISSUE_TEMPLATE.md` — шаблон задачи.
- `PULL_REQUEST_TEMPLATE.md` — шаблон PR.

Вы можете вынести их в `.github/ISSUE_TEMPLATE/` и `.github/pull_request_template.md`, если используете расширенный формат GitHub.

### 4.3 Actions (пример)

Пример упрощённого workflow (для справки, не создан в репозитории):

```yaml
name: CI
on:
  push:
    branches: [ master, main ]
  pull_request:
    branches: [ master, main ]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm test
```

## 5. GitLab (включая self‑hosted)

### 5.1 Потоки разработки

Для GitLab рекомендуется использовать:

- Protected branches для `master`/`main`.  
- Merge Requests с обязательным review.
- Labels для типов изменений (`ai`, `web3`, `ui`, `docs`, `infra`).

### 5.2 GitLab CI/CD (пример)

Пример `.gitlab-ci.yml` для базовой проверки (для справки):

```yaml
stages:
  - test

variables:
  NODE_ENV: test

cache:
  paths:
    - node_modules/

unit_tests:
  stage: test
  image: node:20
  script:
    - npm ci
    - npm test
```

## 6. Bitbucket

- Используйте Pull Requests и Branch Permissions для защиты основной ветки.
- Возможна интеграция с Bitbucket Pipelines по аналогии с примерами CI выше.

Bitbucket подходит как зеркало или основная платформа — структура репозитория нейтральна.

---

## 7. Gitea / Forgejo и др. self‑hosted решения

Для Gitea/Forgejo:

- Настройте:
  - обязательные review для основной ветки;
  - статусные проверки (CI) через webhooks или внешние системы;
  - зеркалирование с/на GitHub или другую публичную площадку (при необходимости).
- Используйте те же веточные стратегии и шаблоны коммитов.

---

## 8. Отечественные Git‑платформы (GitFlic и др.)

Во многих случаях отечественные решения основаны на GitLab CE / Gitea / аналогичных движках, поэтому применимы те же принципы.

Рекомендации:

1. **Зеркало репозитория**
   - Создайте зеркало `metr-mobile` на выбранной платформе (GitFlic и др.).
   - Настройте периодическую синхронизацию с основным upstream (или наоборот, если ваша платформа — главный источник).

2. **Изоляция от внешнего интернета**
   - При необходимости работы в изолированном контуре:
     - перенесите зависимости в локальный npm‑registry;
     - зафиксируйте версии пакетов в `package-lock.json`;
     - используйте artifacts кэши в CI.

3. **Интеграция с отечественными CI/CD**
   - Большинство платформ поддерживает запуск CI на основе `.gitlab-ci.yml`/`*.yml` конфигов или графических пайплайнов.
   - Используйте примеры из разделов 5–7 как основу и адаптируйте под конкретную систему.

4. **Правовые ограничения и лицензии**
   - Убедитесь, что `LICENSE.txt`, `NOTICE.txt` и `LICENSE_METR.md` доступны в интерфейсе платформы.  
   - При форках и внутренних модификациях сохраняйте Apache 2.0 требования (см. `LICENSE_METR.md`).

## 9. Работа с субмодулями и зеркалами

Если вы хотите использовать METR как субмодуль в другом репозитории:

```bash
git submodule add <url-на-metr-mobile> external/metr-mobile
```

Рекомендации:

- Фиксируйте конкретные коммиты/теги METR в вашем продукте.  
- Обновляйте субмодуль только после прохождения всех тестов.
